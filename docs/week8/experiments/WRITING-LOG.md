## 글의 뼈대 (가설)

블랙 프라이데이처럼 피크가 극단적으로 짧고 높은 트래픽은 **스케일업/아웃으로 못 막는다**(DB·PG가 스케일 한계, 오토스케일이 반응하기 전에 터짐). 핵심은 **시스템이 감당하는 속도로 요청을 흘려보내는 것(Back-pressure)** 이고, 대기열은 그 구현이다. Rate Limiting(거부)이 아니라 Queuing(보관)을 택하는 이유는 **유저가 기다릴 의사가 있는** 워크로드이기 때문 — "나중에 다시 시도"는 재시도 폭풍을 부른다.

단, **대기열은 피크를 평탄화(smoothing)할 뿐 부하를 없애지 않는다.** 토큰을 한 번에 쏟으면 Thundering Herd로 원래 문제의 축소판이 재발한다. 그래서 이번 라운드의 판단 축은:

1. **거부 vs 줄세우기** — 왜 이 상황에서 Queuing인가
2. **스케줄러 배치 크기** — 하류(주문 API + DB) 실제 처리량에서 역산한 근거
3. **Thundering Herd** — 발급 분산으로 무엇을 바꾸는가
4. **장애 시 계약** — Redis가 죽으면 우리 서비스는 어떻게 동작해야 하는가(사후 판단은 늦다)
5. **Polling vs SSE** — 왜 그 피드백 방식인가

- 대기열은 **주문 API 앞단의 관문**이고, 주문 이후는 R7 이벤트 파이프라인(Outbox → Kafka → streamer)이 그대로 동작한다.
- 전체 요구사항: `../00-requirements.html` / 체크리스트: `../checklist.md`

### 결정 1 — 보호 대상은 `POST /orders` 하나, 토큰은 주문 생성까지만

- 요구사항 명시 흐름이 `enter → position 폴링 → 토큰 → POST /orders → 검증 → 처리 → 삭제`로 닫혀 있고, 결제는 미등장.
- 우리 코드베이스는 주문(`place()` → PENDING_PAYMENT)과 결제(`POST /payments`)가 분리라 "주문 완료 후 삭제"의 해석 여지가 있었음 → **문언 그대로 주문 생성 성공 시 DEL**. 결제 보호는 Rate Limit(Nice) 축으로 분리.
- 일반화: **대기열은 페이지 입장이 아니라 "행위" 단위로도 건다** — 상용(Cloudflare/NetFUNNEL)은 페이지 입장 대기열, 우리는 주문 액션 대기열. 진입점 = "주문하기" 클릭.

### 결정 2 — 재진입 = `ZADD NX` (최초 진입 시각 보존)

- 논의 발단: "재접속 시 빼고 다시 넣는 게 보통 아닌가" → 검토 결과 **반려**. ZADD 기본 동작은 기존 member의 score **덮어쓰기**라, 재삽입하면 새로고침한 정상 유저가 뒤로 밀림(공정성 파괴).
- "빼고 다시 넣기"가 정당한 건 score=heartbeat(이탈 감지) 모델일 때 — FIFO 공정성을 포기하고 sweeper가 붙는 다른 설계다. 과제 요구는 FIFO.
- Set의 dedup은 "중복 엔트리 방지"만 보장하고 "순번 보존"은 보장하지 않는다 — 그 갱신을 막는 스위치가 NX. (글 포인트: **자료구조의 유일성 보장과 순서 보장은 별개 축이다**)

### 결정 3 — Redis 장애 = fail-close, 부하 실측 = 로컬까지

- 주문은 재고·결제가 걸린 정합성 민감 경로 → 쿠폰 게이트키퍼의 fail-open(장애 시 통과)과 반대로 **전면 차단**. "Redis 죽으면 어떻게 되는가"를 장애 전에 계약으로 박아둠(요구사항의 Graceful Degradation 질문에 대한 답).
- 확장 아이디어(리서치 수확): AWS는 하류 사용률 알람이 OK일 때만 inlet 증가 — "Redis 생존 + 하류 불건강" 케이스에 스케줄러 일시정지 게이트가 자연 확장(Nice).
- EC2 SUT+k6는 금 18:00 마감 예산상 스킵 — R7에서 실측 근육은 이미 만들었고, 이번 검증 목표는 동시성·정확성(Testcontainers)이다.

### 결정 4 — 만료 유저는 재진입(맨 뒤)

- 토큰 TTL(5분) 소진 유저에게 우선권을 줄지 명시가 없음 → **재진입**. "기회를 받았는데 안 쓴 것"이므로 맨 뒤가 공정성 논리로 방어됨 + 우선권은 별도 자료구조/정책 복잡도만 추가(YAGNI).

### 결정 5 — 토큰 TTL 기본 5분, 프로퍼티로 외부화

- "5분이 짧지 않나" 검토 → **TTL은 통념이 아니라 커버 행위 길이로 정한다.** 우리 토큰은 주문서 확인→접수까지만 커버(결정 1, 결제 미포함)라 행위가 1~2분 → 5분이면 2~3배 여유. 결제까지 커버했다면 5분은 실제로 짧았을 것 — 스코프를 좁힌 결정 1이 TTL도 빡빡하게 유지시켜 준다(결정들이 맞물리는 지점, 글감).
- 검증된 외부 앵커: Cloudflare Waiting Room session duration **기본 5분(1~30분 범위)** — 딥다이브 [10].
- **TTL↑의 비용**: 최악 동시 유효 토큰 수 = 발급 속도 × TTL. TTL 2배 = 주문 API 동시 유입 상한 2배 → 대기열로 지킨 걸 토큰 창구에서 도로 여는 셈.
- 만료=재진입(결정 4)과의 균형: 행위 시간의 2~3배를 주고도 안 쓴 경우라야 "맨 뒤로" 논리가 방어됨. TTL이 행위 시간과 비슷하면 정상 유저도 만료돼 논리가 무너진다.
- 정책 값이므로 코드 상수가 아니라 `queue.token.ttl-seconds` 프로퍼티. 운영 지표(발급 대비 미사용 만료율)를 보고 조정하는 손잡이.

### 예외 전수 점검 — 상태 3개(대기/입장/무상태) × 비정상 행동 매트릭스

- 새로고침 재진입(NX no-op)·우회 주문(검증 거부)·잠적(자연 배수)·두 탭 동시(member 유일성)·만료 후 주문(409)·실패 재시도(토큰 유지) — 전부 ZADD NX · SET NX · TTL · 검증 4개 장치가 자동으로 받아냄. **설계가 못 받는 구멍 2개 발견**:
  - **구멍 1 — 토큰 보유 중 재진입**: 입장자는 ZSET에 없어 NX가 못 막음 → 주문서 작성+다음 줄서기 파이프라이닝 가능. 처방: enter에서 토큰 보유자 거부 (열린 결정 ⑫).
  - **구멍 2 — 검증(GET)·소모(DEL) 분리 race**: 더블클릭 2발 동시 검증 통과 가능. 수용+문서화 권장 — 대기열 책임은 유량 제어, 중복 주문 방지는 주문 도메인 몫(관심사 분리 논거가 글감). GETDEL 원자화는 "실패=유지" 정책과 충돌 (열린 결정 ⑬).

### 복잡도 감사 — "Redis에서 긴 복잡도는 나쁘다"의 정확한 의미

- Redis는 싱글 스레드 → O(N) 명령 하나가 폴링 수만 건을 전부 세움(head-of-line blocking). 점검 기준은 평균이 아니라 **최악 단일 명령의 유계성**.
- 감사 결과: 유저 유발 명령 전부 O(log N) 이하(N=100만이어도 ~20스텝), 스케줄러만 O(M log N)인데 M은 프로퍼티 상수. **설계에 O(N) 없음.**
- 위험은 운영 습관: `KEYS`(절대 금지)·`ZRANGE 0 -1`·거대 키 `DEL`(→UNLINK). 금지 목록을 03 문서에 명문화.
- Lua 블로킹이 M에 선형 → "1초에 140명보다 100ms에 14명" 논거의 수치적 근거.

### 아키텍처 3안 비교 — 블로그 척추 확정 (`../03-architecture-options.html`)

- ① Sorted Set 드레인(채택·과제 명시) vs ② Serving Counter(AWS — 진짜 경쟁자) vs ③ Kafka 로그(탈락 — 순번 조회 불가 하나로 충분).
- 글의 구조: "Sorted Set으로 만들었다"가 아니라 **"②와 견줘보니 ①의 구멍(ZPOPMIN 원자성·어뷰징·만료 유량 손실·폴링 스파이크)이 보였고, ②의 처방을 이식해 막았다"**. ①의 약점 4개 ↔ ②의 처방 4개 매핑 표가 03 문서 §5.
- 비교의 교훈: 셋 중 전부 이기는 안은 없다 — ③도 R7 쿠폰(순번 노출 불필요) 워크로드에선 최선. 아키텍처 선택은 워크로드 종속.

- 상용 대기실(Cloudflare/Queue-it/티켓팅)에서 토큰 발급은 유저에게 안내되지 않음 — 쿠키/세션에 자동 저장, 유저 체감은 "내 차례가 되면 자동 이동"뿐. 단 **TTL은 "N분 내 완료" 제한 시간 타이머로는 노출**하는 게 표준(공정성 — 시간 안에 마쳐야 함을 알아야 하므로). 02-user-journey ④⑤는 설계 문서라 의도적으로 드러낸 것.

### 리서치 수확 — 구현에 직접 닿는 것 (상세: 01-deep-dive §10)

- **토큰 멱등 발급**: 재요청 시 새 TTL 토큰이 아니라 기존 토큰 반환(AWS generate_token idempotent) → `SET NX`로 자연 획득.
- **ZPOPMIN 원자성 카드(열린)**: 꺼냄→발급 사이 장애 시 유저 증발. serving counter 모델(순번 비교)엔 구조적으로 없는 문제 — 대비가 글감.
- **동일 score는 사전순**: 같은 ms 진입자는 userId 사전순 = 엄밀 FIFO 아님. 수용+문서화.
- **같은 앱 안의 대기열은 Redis-only 초경량 경로여야** — 대형 사업자가 대기열을 엣지로 빼는 이유(보호 장치가 보호 대상과 같이 죽으면 안 됨)가 우리 안에서 재현됨. `/queue/*`는 DB 접근 0.
