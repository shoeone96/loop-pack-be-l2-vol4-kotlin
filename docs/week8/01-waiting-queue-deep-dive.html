ARCHITECTURE PATTERNS

아키텍처 패턴 4종 — 어디에 대기열을 두는가

대기열은 보호 대상보다 앞에 있어야 합니다. "얼마나 앞"인지에 따라 4개 패턴이 갈립니다 — 앱 레이어(자체 구축) → 클라우드 인프라 → CDN·엣지 → 아예 요청 자체를 큐로.

AWS 레퍼런스의 두 가지 교훈 (deprecated여도 남는 것)

AWS 공식 솔루션은 폐기됐지만(현 권장은 CloudFront Functions 기반 방문자 우선순위화[2]), 설계 두 가지는 여전히 표준입니다.

(a) 진입조차 비동기로. 대기열 진입 요청을 즉시 처리하지 않고 SQS에 넣어 Lambda가 배치(최대 10건)로 처리합니다 — "순번 발급" 자체가 폭주 지점이 될 수 있어서, 진입 API는 요청 ID만 즉시 반환하고 순번은 나중에 폴링으로 확인시킵니다.[1] 대기열의 문 앞에도 또 하나의 작은 큐가 있는 셈입니다.

(b) serving counter 모델. 입장 게이트를 "스케줄러가 사람을 꺼내는" 대신 카운터 비교로 봅니다: 각자 순번(queue position)을 받고, 전역 serving counter가 내 순번 이상이 되는 순간 토큰 발급 자격이 생깁니다.[2] 입장 정책(시간/인원 기반)은 "카운터를 언제 얼마나 올리는가"로 추상화됩니다 — 정책과 메커니즘의 분리.

우리 과제와의 대응 우리 ZPOPMIN 스케줄러는 "꺼내는" 모델이라 counter 비교 모델과 구현은 다르지만 등가입니다 — 스케줄러 주기·배치 크기가 곧 inlet strategy입니다. 차이 하나: ZPOPMIN은 꺼낸 뒤 순번 정보가 사라지므로, 토큰을 못 받은 채 증발하는 유저가 없도록 "꺼냄 → 토큰 발급"이 원자적이어야 합니다(꺼내고 죽으면 그 유저는 대기열에도 토큰에도 없음). counter 모델은 이 문제가 구조적으로 없습니다 — 설계 결정 카드감.

ADMISSION CONTROL

입장 제어 — 시간 기반 vs 인원 수 기반

"입장을 어떻게 흘려보내는가"는 조사 전체에서 가장 갈리는 지점이었습니다. 실무 구현들은 둘 중 하나가 아니라 대부분 하이브리드였습니다.

 시간 기반 (rate)인원 수 기반 (slot / concurrency)하이브리드
원리주기마다 N명 방출"활성 사용자 수 상한" 유지 — 나가야(완료/이탈) 다음이 들어옴동시 상한 + 분당 유입 상한 동시 적용
실제 구현AWS Periodic inlet(1분마다 고정 수)[2] · Queue-it throughput rate[14] · NetFUNNEL 초당 N명[19] · 우리 스케줄러AWS MaxSize inlet(완료/이탈 알림만큼 counter 증가)[2] · SeatGeek leaky bucket(bucket=보호구역 정원, 초과 시 429)[8][21]Cloudflare: Total Active Users + New Users Per Minute, 먼저 걸리는 한도[10] · SeatGeek: 정원 상한+rate 방출[8]
하류 보호간접 — "방출률 ≈ 처리율" 가정이 맞을 때만직접 — 동시 부하 자체에 상한직접 + 유입 평활
필요한 신호처리율 실측(사전)세션 종료 신호 — 완료 이벤트/heartbeat/session TTL둘 다
실패 모드처리 지연 시에도 계속 방출 → 하류 적체이탈을 못 감지하면 슬롯 누수 → 대기열 기아(starvation)구현 복잡도

실무의 답: rate로 흘리되, 부하 신호로 멈춘다

순수 시간 기반의 약점은 "하류가 아픈데도 계속 방출"입니다. AWS Periodic inlet은 그래서 CloudWatch 알람이 OK일 때만 카운터를 올리는 옵션을 붙였습니다 — 사이트 사용률 지표가 나쁘면 입장 자동 중지.[2] Cloudflare는 아예 두 상한을 동시에 겁니다: 분당 유입(rate)과 동시 활성 수(slot) 중 먼저 걸리는 쪽이 이깁니다.[10]

인원 수 기반의 약점은 반대로 "나감"을 알아야 한다는 것입니다. Cloudflare는 session duration(1~30분, 기본 5분) 쿠키 만료로 슬롯을 회수하고[10], AWS MaxSize는 사이트 측이 완료(exited)/이탈(abandoned) request ID 목록을 SNS로 보내주는 만큼만 다음 인원을 들입니다.[2] 이 신호 체계가 없으면 인원 수 기반은 성립하지 않습니다.

R8 판단 과제 Must는 시간 기반 스케줄러로 충족됩니다. 다만 "토큰 미사용 만료분만큼 다음 유저에게 추가 발급"이라는 과제 요구가 사실 인원 수 기반의 슬롯 회수 개념입니다 — 즉 과제 자체가 이미 하이브리드를 반쯤 요구하고 있습니다. 글감: "시간 기반으로 시작해 만료 회수를 붙이니 하이브리드가 됐다".

ENTRY TOKEN DESIGN

슬롯 회수 3종 — "받고 안 쓰는 자리"를 되찾는 법

  • 만료 자동 회수 — AWS queue_pos_expiry: 순번 자체에 TTL을 두고, 만료돼 토큰을 못 받은 순번만큼 serving counter를 자동 증가 → 이탈자 때문에 대기열이 멈추지 않음[2]. 우리 과제의 "만료분만큼 추가 발급"과 동일 개념
  • 능동 회수(revocation) — Cloudflare: 오리진이 응답 헤더 Cf-Waiting-Room-Command로 세션 취소를 명령해 활성 슬롯을 조기 회수 → 처리량 개선[7]. 우리의 "주문 완료 시 DEL"이 이 축의 최소형
  • 라이프사이클 연동 — SeatGeek: 토큰은 구매 완료 또는 이탈 시 만료 — 토큰 수명을 비즈니스 이벤트에 묶음[8]
two-token 패턴 SeatGeek은 토큰을 둘로 나눕니다: 도착 시 visitor token(도착 timestamp 보유 = 대기 자격)을 주고, 순번이 되면 access token(입장 자격)으로 교환합니다.[21] 우리 설계에선 Sorted Set 멤버십이 visitor token 역할, entry-token이 access token 역할 — 같은 구조를 저장소 두 개로 푼 셈입니다.

POSITION FEEDBACK

순번 피드백 — Polling이 기본인 이유

조사 결과가 명확합니다: AWS·Cloudflare·NetFUNNEL 모두 polling이 기본이고, push(WebSocket)는 SeatGeek 하나였습니다. 대기열 피드백은 단방향·저빈도라 polling의 약점이 거의 드러나지 않기 때문입니다.

Polling을 제대로 하는 법 — 서버가 주기를 정하고, 흔든다

Cloudflare의 디테일이 배울 점입니다. JSON 응답에 refreshIntervalSeconds를 담아 다음 폴링 시점을 서버가 지정하고, 유저마다 의사난수 오프셋을 더해 체크인 시점을 분산합니다 — 대기 인원 전체가 같은 초에 폴링하는 self-inflicted thundering herd를 서버가 예방하는 것입니다. 슬롯 방출도 고정 주기가 아니라 무작위 시점에 해서, 체크인 타이밍을 노린 편법을 막습니다.[6]

예상 대기시간 — 단일값이 아니라 범위로

기본 산식은 내 순번 / 초당 처리율이지만, Cloudflare는 random queueing에서 확률 기반 산식 n = log(1-p) / log(1-P(입장/분))으로 percentile을 계산해 "5분~15분" 범위로 표시합니다.[6] 추정치를 단정하지 말고 범위·"약"으로 말하라는 요구사항과 같은 결론입니다.

FAIRNESS

공정성 — FIFO의 함정과 4가지 대안

직관과 달리, 조사에서 가장 강한 반전은 "FIFO가 공정성의 유일한 답이 아니다"였습니다 — 대기열 벤더 스스로가 이렇게 말합니다.

"FIFO 대기열의 판매는 판매 시작 시각이 아니라, 대기열이 열리는 시각에 사실상 시작된다."

Queue-it — Why First-In-First-Out Queuing Isn't (Always) The Answer[15]

스케줄된 판매(티켓팅·플래시세일)에서 순수 FIFO는 밀리초 단위 도착 경쟁이 되고, 그 경쟁은 초고속 회선과 스캘핑 봇이 구조적으로 이깁니다.[15] Cloudflare도 같은 이유(+늦게 온 유저가 긴 대기시간을 보고 이탈하는 문제)로 random queueing을 도입했습니다.[6]

FIFO최초 도착 timestamp 순[11]평시·상시 트래픽 — 정확한 대기시간 예측 가능
Random도착 시간 무관, 슬롯 열릴 때 무작위 선발[11]단기 하이프 이벤트(출시·한정판) — 형평 분배[6]
Pre-queue + 추첨판매 전 도착자는 추첨으로 순번 배정, 이후 도착자만 FIFO[14][15]예고된 오픈 시각 — 조기 접속 이점 무력화
Passthrough / Reject전부 통과(계측만) / 전부 거부[11]평시 모니터링 / 긴급 차단

우리 구현의 공정성 디테일 — Redis 공식 문서에서 나온 함정 2개

  • 확정재진입 = ZADD NX. ZADD는 기존 멤버를 만나면 score를 덮어씁니다(순번 뒤로 밀림). NX가 "있으면 건드리지 않음"으로 최초 진입 시각을 보존 — 공식 문서가 이 플래그를 명시[13]. (우리 결정 ②의 공식 근거)
  • 신규동일 score의 순서는 도착순이 아니다. score가 같으면 멤버 문자열 사전순(lexicographical)으로 정렬됩니다[12]. 같은 밀리초에 진입한 유저끼리는 userId 사전순 — 엄밀한 FIFO가 아님. 대응: score 해상도를 ms로 + 동률 허용(실용) vs score에 시퀀스 결합(엄밀). 우리 규모(과제)에선 전자로 충분하되 한계를 문서화.
  • 중복 진입 방지 — Sorted Set 멤버 유일성(구조적) + 세션 추적. SeatGeek은 first-party 쿠키 + 동일 토큰 동시 사용 차단을 권고[8]

ABUSE & BOTS

어뷰징 · 봇 — 대기열이 뚫리는 방식

대기열의 맹점: 트래픽의 "양"만 보고 "품질"을 보지 않는다는 것.[23] 봇은 대기열을 우회하는 게 아니라 대기열에 성실하게 줄을 서서 이깁니다.

공격 패턴메커니즘실무 대응
다중 점유봇이 여러 자리를 동시에 점유 → 실사용자 대기시간 증가. 게다가 차례가 와도 입장하지 않아(쿠키 미처리) 큐 진행 자체를 정체시킴[7]진입 시 봇 스코어 연동 — 봇은 뒤로/차단[7]
도착 경쟁 승리FIFO의 밀리초 경쟁을 스캘핑 봇이 이김[15]pre-queue 추첨(§6)
잠복 후 활동진입 시 1회만 신뢰 판정 → 봇이 인간처럼 진입 후 내부에서 활동(dormant-then-activate)[23]지속 검증(continuous validation) — 입장 후에도 행동 재평가[23]
토큰 재발급 어뷰징같은 자격으로 새 만료시간 토큰을 반복 발급멱등 발급 — 같은 요청 ID → 항상 같은 토큰[2]

Infinite Queue — 차단 대신 가짜 대기열로

Cloudflare의 재밌는 설계: 챌린지(Turnstile — 대기 중에만 제시, 입장 후엔 없음)에 실패한 트래픽을 차단하지 않고 Infinite Queue로 보냅니다. 정상 대기 화면과 똑같지만 예상 대기시간이 점근 곡선이라 절대 0에 도달하지 않는 가짜 대기열 — 봇이 차단을 인지하는 시간을 늦추고 리소스를 소모시킵니다. 챌린지를 실행한 "유저"의 약 5%가 통과하지 못했다고 관측됩니다.[7]

R8 범위 판단 봇 대응은 과제 범위 밖입니다(로그인 사용자 대상 + userId 유일성으로 기본 방어). 단 "userId는 인증 컨텍스트에서"(R7 결정 4)가 사실 이 축의 최소 방어선이라는 연결은 글감이 됩니다 — 자칭 식별자를 믿는 순간 다중 점유가 무료가 됩니다.

OPERATIONS

운영 — Thundering Herd · 장애 · 지표

요구사항이 경고한 "토큰 발급 직후의 함정"을 실무는 발급 전·중·후 세 지점에서 나눠 막습니다.

지점기법출처
진입(전)진입 요청을 큐에 넣어 배치 처리 — 순번 발급 자체를 비동기로AWS SQS 배칭[1]
발급(중)발급 간격 분산(100ms 단위 소량) + 슬롯 무작위 방출 + 토큰 활성화 jitterCloudflare 무작위 방출[6] · 과제 명세

재시도(후)jittered backoff — 동일 스케줄 재시도는 클라이언트를 재동기화시켜 herd 재생성Redis 공식 블로그[3]
키 만료TTL에 jitter(예: 1시간 의도 시 55~65분 랜덤) — 대량 키 동시 만료 방지Redis 공식 블로그[3]

Redis가 오히려 herd를 만드는 경우

주의: Redis는 herd 방어 도구지만, 동기화된 만료·빈 캐시로 동시에 뜨는 오토스케일 인스턴스 조합에선 load buffering이 아니라 load amplification이 됩니다.[3] 캐시 미스 시엔 request coalescing(분산 락으로 한 요청만 DB 조회, Lua로 in-progress 마킹)이 표준 처방입니다.[3]

장애 시 — 입장을 멈추는 신호부터

AWS 패턴의 핵심은 degradation을 별도 기능이 아니라 inlet에 내장한 것입니다: 백엔드 사용률 알람이 OK가 아니면 카운터 증가를 건너뜀 = 입장 자동 중지.[2] 우리의 fail-close 결정(Redis 죽으면 전면 차단)과 방향이 같고, 한 단계 더 — Redis가 살아 있어도 하류(DB)가 아프면 스케줄러가 쉬는 게이트를 붙일 수 있습니다(Nice 후보).

지표 — 요구사항 6종 + 실무 추가분

요구사항의 Queue Depth·Avg/P99 Wait·Token Conversion/Expiry·Scheduler Health에 더해, 실무는 이탈(abandonment)을 별도 신호로 봅니다: AWS는 완료(exited)와 이탈(abandoned)을 구분해 슬롯 회수량을 계산하고[2], Cloudflare는 봇 격리 대기열의 새로고침 횟수(infinite queue refreshes)까지 셉니다.[7]

KOREAN CASES

한국 실무 사례 — 대기열 vs 수량 통제

국내 사례를 조사하며 분명해진 구분: "대기열(waiting room)"과 "수량 통제(선착순 쿠폰)"는 다른 문제입니다. 전자는 순서와 입장을, 후자는 정합성(초과 발급 0)을 지킵니다. R7이 후자였고 R8이 전자입니다.

사례문제구조배울 점
NetFUNNEL[19]티켓팅 대기열 (멜론티켓·인터파크·예스24 등 채택)임계치 초과 시 가상 대기실 자동 생성 → 선착순 티켓(입장 토큰) 발급 → 초당 N명 순차 입장 + 우회 차단 키 체크국내 티켓팅 표준이 시간 기반 admission — 우리 스케줄러와 같은 모델
여기어때 네고왕[16]선착순 쿠폰 (수량 통제)Redis SET에 SCARD+SADD를 MULTI/EXEC로 원자 판정 → Kafka(파티션 3)로 발급 비동기화. 피크 동접 28,800+, TPS 3,600+INCR→SET→SET+Tx 3단계 진화 — 원자성 없는 판정은 고부하에서 초과 지급. ⚠️ Redis Tx는 rollback 없음 + Standalone 전용
올리브영 올영세일[17]선착순 쿠폰 미발급 0.014~1.62% 문제GET/INCR 분리가 race 유발 → Lua 원자화(성능 -21%) → 듀얼 카운터(요청 카운터 선증가, 성능 -8%)로 미발급 0 달성원자성 확보 방식마다 성능 비용이 다르다 — 정량 트레이드오프의 모범
토스[18]스파이크가 DB insert QPS 한계 초과Kafka 비동기 적재 + Consumer 스로틀링으로 최대 QPS 제어outflow rate 제어를 컨슈머 쪽에서 — R7 파이프라인과 같은 축
R8의 위치 여기어때·올리브영·토스는 전부 "요청을 받아들인 뒤"의 수량·유량 통제입니다. R8 대기열은 그보다 앞 — 요청이 API에 닿는 것 자체를 조절합니다. 국내 사례 중 이 위치에 있는 것이 NetFUNNEL(상용)이고, 우리는 그걸 Redis Sorted Set으로 자체 구축하는 셈입니다. 이 위치 구분이 블로그 글의 뼈대가 될 수 있습니다: "선착순 쿠폰(R7)과 주문 대기열(R8)은 왜 다른 문제인가".

TAKEAWAYS FOR R8

R8 설계 시사점

이 조사가 우리 구현 결정에 직접 닿는 지점들입니다. Must 범위는 그대로 두고, 근거가 더 단단해진 것과 새로 생긴 결정 카드를 구분했습니다.

  • 결정 ② (ZADD NX) 공식 근거 확보 — ZADD 기본 동작은 score 덮어쓰기, NX가 최초 진입 보존[13]. Cloudflare FIFO도 "최초 도착 timestamp 보존" 모델[11]
  • 결정 ④ (fail-close) 강화 근거 — AWS는 하류 부하 알람을 inlet에 연동해 입장 자동 중지[2]. "Redis 장애 = 차단"에 더해 "하류 불건강 = 스케줄러 일시정지" 게이트가 자연 확장(Nice 후보)
  • NEW동일 score 사전순 문제 — 같은 ms 진입자는 userId 사전순[12]. 과제 규모에선 수용하되 한계를 checklist·글에 명시
  • NEWZPOPMIN 원자성 카드 — "꺼냄→토큰 발급" 사이에 죽으면 유저 증발(대기열에도 토큰에도 없음). Lua로 묶거나, 꺼낸 목록 처리 실패 시 복구 경로를 정의해야 함. serving counter 모델엔 없는 문제라는 대비가 글감
  • NEW토큰 멱등 발급 — 재요청 시 새 토큰(새 TTL)이 아니라 기존 토큰 반환[2]. 우리 구현에선 SET NX로 자연 획득 가능 — 발급 로직에 명시
  • NEW폴링 주기의 서버 제어 — 응답에 다음 폴링 간격 포함(+jitter)[6]. "순번 구간별 동적 주기"(Nice)의 구현 형태로 채택 가치
  • 시간 기반 + 만료 회수 = 사실상 하이브리드 — 과제 요구 자체가 이미 슬롯 회수 개념을 포함(§3). 블로그 주제 "스케줄러 배치 크기 산정"과 묶으면 입체적
출처 관련 주의 AWS Virtual Waiting Room 솔루션은 2025-11 GitHub 아카이브·공식 문서 404 상태입니다(현 권장: CloudFront Functions 방문자 우선순위화). 본문 인용은 살아있는 공식 블로그·GitHub 저장소 기준이며, "폐기된 레퍼런스 아키텍처의 패턴"으로만 인용해야 합니다 — 최신 AWS 권장 사항으로 쓰면 부정확합니다.
