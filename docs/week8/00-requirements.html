SCOPE AT A GLANCE

한눈에 보기 — Must-Have vs Nice-To-Have

Rate Limiting은 초과 요청을 거부(429)하고, Queuing은 보관합니다. 블랙 프라이데이처럼 유저가 기다릴 의사가 있는 트래픽에서 "나중에 다시 시도"는 재시도 폭풍을 부릅니다. 그래서 이번엔 거부가 아니라 줄 세우기를 구현합니다.

MUST 무조건 구현

Redis Sorted Set 대기열 · 입장 토큰 발급/검증(TTL) · 스케줄러 기반 순차 입장 · Polling 순번 조회. 이 네 축이 Round 8의 합격선입니다.

NICE 시간 되면

SSE 실시간 Push · Polling 주기 동적 조절 · Thundering Herd 완화(분산/Jitter) · Redis 장애 시 Graceful Degradation. Must가 끝난 뒤에 손댑니다.

왜 스케일업/아웃이 답이 아닌가 서버를 10배 늘려도 DB와 PG는 스케일이 제한적이고, 피크가 극단적으로 짧고 높으면(행사 시작 직후 10초) 오토스케일이 반응하기 전에 터집니다. 결국 시스템이 처리할 수 있는 속도로 요청을 조절(Back-pressure)하는 것이 핵심이고, 대기열은 그 대표적 구현입니다.

STEP 1 · WAITING QUEUE

Redis Sorted Set 대기열

유저 요청을 진입 순서대로 보관하고 중복 진입을 방지합니다. Sorted Set은 score(진입 시각)로 정렬되고 member(userId)는 집합이라 유일합니다 — 이 둘이 "공정한 순서 + 중복 방지"를 동시에 해결합니다.

명령역할키 · 의미
ZADD대기열 진입queue:orders {timestamp} {userId}
ZRANK내 순번 조회 (0-based)queue:orders {userId}
ZCARD전체 대기 인원queue:orders
ZPOPMIN앞에서 N명 꺼내기 (스케줄러)queue:orders {N}
  • MUST진입 API POST /api/v1/queue/enter — ZADD, score=진입 시각. userId는 body 아닌 인증 컨텍스트에서 (R7 결정 4: 자칭 식별자 금지)
  • MUST순번 조회 API GET /api/v1/queue/position — ZRANK 결과 +1 을 사람이 읽는 순번으로
  • MUST중복 진입 방지 — Sorted Set member 유일성으로 자연 방지. 재진입 시 최초 진입 시각 유지 여부는 결정 사항
  • MUST전체 대기 인원 — ZCARD (운영 지표 Queue Depth 겸용)
과설계 경계 단순 ZADD/ZRANK는 단일 원자 명령이라 쿠폰 게이트키퍼처럼 Lua 스크립트가 꼭 필요하지 않을 수 있습니다. 여러 명령을 하나의 원자 단위로 묶어야 할 때(예: 정원 확인 + 진입)만 Lua를 도입하고, 근거를 Writing Log에 남깁니다.

STEP 2 · ENTRY TOKEN & SCHEDULER

입장 토큰 & 스케줄러

스케줄러가 일정 주기로 대기열 앞에서 N명씩 꺼내 입장 토큰을 발급합니다. 토큰은 TTL이 있어 시간 내 쓰지 않으면 자동 만료되고, 토큰이 있는 유저만 주문 API에 진입합니다.

  • MUST배치 드레인 스케줄러 — @Scheduled 주기 실행 → ZPOPMIN N → 토큰 발급. @ConditionalOnProperty on/off (OutboxRelay 컨벤션 답습)
  • MUST입장 토큰 발급 — SET entry-token:{userId} {token} EX {ttl} (예: 5분). 순번 조회 응답에 포함되어 유저에게 전달
  • MUST주문 진입 시 토큰 검증 — 주문 컨트롤러 앞단에서 토큰 확인 → 없으면 거부. FCFS Gatekeeper.tryPass() 진입부 호출 패턴 참고
  • MUST주문 완료 후 토큰 삭제 — DEL entry-token:{userId} (재사용 차단)
  • MUST배치 크기 산정 근거 문서화 — 처리량 기준으로 스케줄러 배치 크기 산정 (아래 계산)
처리량 설계 기준 — 예시가 아니라 실제 수치로 요구사항 예시: DB 커넥션 풀 50 · 주문 1건 200ms → 이론 최대 250 TPS → 안전 마진 70% = 175 TPS → 100ms마다 ~18명 발급. 단 이 수치를 그대로 베끼지 말고 우리 프로젝트의 실제 Hikari 풀 크기·주문 처리 시간으로 다시 산정해 Writing Log에 근거를 남깁니다.
⚠ 토큰 미사용 = 자리만 차지 토큰 받고 주문 안 하면 그 슬롯이 낭비됩니다. TTL 만료 처리는 필수이고, 만료된 토큰 수만큼 다음 유저에게 추가 발급하는 로직이 필요합니다.

STEP 3 · REAL-TIME POSITION

실시간 순번 조회 (Polling)

대기열의 성패는 유저가 기다리는 동안 이탈하지 않느냐에 달려 있습니다. 순번이 안 보이면 유저는 새로고침하거나 떠납니다. 순번만 주는 것보다 "약 N분 남았습니다"가 훨씬 효과적입니다.

  • MUST예상 대기 시간 계산 — 내 순번 / 초당 처리량. 추정값이므로 "약 N분/초" 표현
  • MUSTPolling 응답 통합 — { position, estimatedWaitSeconds, token? }. 순번 0 도달 시 토큰 포함 반환
  • MUSTPolling 부하 고려 — 대기 인원 × 조회 주기 = 초당 조회량. Redis라 감당 가능하나 근거 명시

NOW Polling

클라이언트가 1~3초마다 순번을 질의. 구현 단순·인프라 변경 없음. 대기 인원이 많으면 Polling 자체가 부하 + 주기만큼 지연. 이번 라운드는 여기서 시작.

NEXT SSE

서버가 순번 변경 시점에만 Push. 불필요한 요청 없음. 대기 인원 × 커넥션 유지 필요. Polling 부하가 문제 될 때 전환(Nice-To-Have). WebSocket은 단방향이면 충분해 과도.

VERIFICATION

검증 — 통과해야 할 3가지

과제 체크리스트가 명시한 검증 항목입니다. 각각을 재현 가능한 테스트로 남깁니다 — 동시성 검증은 R7 CouponIssueGatekeeperIntegrationTest의 runConcurrently 선례를 재사용합니다.

HIDDEN RISKS

숨은 리스크 — Thundering Herd · 장애 · 지표

대기열을 만들었다고 끝이 아닙니다. 대기열은 피크를 평탄화할 뿐 부하를 없애지 않습니다. 토큰을 한 번에 쏟으면 원래 문제의 축소판이 재발합니다.

Thundering Herd — 토큰 발급 직후의 함정

스케줄러가 1초에 175명에게 토큰을 몰아 발급하면 175명이 동시에 주문 API를 때립니다. 완화 3종:

전략내용효과
발급 간격 분산1초 175명 대신 100ms마다 ~18명부하 10배 평탄화
토큰 Jitter활성화 시점에 랜덤 딜레이(0~2s)진입 시점 자연 분산
주문 API Rate Limit토큰 있어도 초당 N건까지만하류 최종 안전장치

Graceful Degradation — Redis가 죽으면?

대기열의 핵심 인프라인 Redis가 죽으면 우리 서비스는 어떻게 동작해야 하는가? 전면 차단(안전·중단) / 대기열 우회(유지·과부하 위험) / Fallback 큐(순번 정확성↓·유지) — 정답은 없습니다. 중요한 건 장애 전에 이 계약을 정의해두는 것. 주문은 쿠폰보다 정합성에 민감하므로 우회 허용은 신중해야 합니다.

운영 지표 — 장애 전에 감지하려면

지표설명왜 중요
Queue Depth현재 대기 인원 (ZCARD)유입 > 처리량 신호
Avg / P99 Wait진입→토큰 발급 대기 시간체감 품질 · 병목 시점
Token Conversion토큰 발급→주문 완료 비율<50%면 TTL/UX 문제
Token Expiry토큰 만료(이탈) 비율>30%면 대기 중 포기
Scheduler Health스케줄러 마지막 실행 시각1분+ 미실행이면 큐 정지
비즈니스 지표 Token Conversion Rate · Token Expiry Rate는 단순 시스템 지표가 아니라 비즈니스 지표입니다. 유저가 토큰을 받고도 주문 안 하면 대기 시간이 너무 길거나 TTL이 안 맞는다는 뜻입니다.
