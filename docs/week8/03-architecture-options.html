OPTION 1 · PULL — 채택안

① Sorted Set 드레인 — 실제 줄에서 꺼낸다

대기열이 물리적인 줄입니다. 유저를 Sorted Set에 넣고(ZADD NX), 순번은 자료구조가 알고 있고(ZRANK), 입장은 스케줄러가 줄 맨 앞에서 실제로 꺼내면서(ZPOPMIN N) 일어납니다.

강점 요구 기능이 자료구조에 내장

순번 조회(ZRANK)·중복 진입 방지(member 유일성)·전체 인원(ZCARD)이 전부 명령 하나입니다. 과제 Must 4개 중 3개가 공짜. 요구사항이 명시한 방식이기도 합니다.

약점 꺼내는 동작의 대가

ZPOPMIN으로 꺼낸 직후 장애가 나면 유저가 대기열에도 토큰에도 없습니다(증발). 대기 인원만큼 메모리 O(N), 순번 조회 O(log N)도 ②보다 비쌉니다.

채택 사례 지마켓 대기열 시스템(Redcarpet)이 같은 계열입니다 — Sorted Set(score=타임스탬프) + ZRANK 순번 조회 + Job이 유입량만큼 단계 이동.[5] 우리 R7 선착순 쿠폰의 "Redis 게이트 + 비동기 처리 + 결과 폴링"과도 동형이라 코드 선례가 리포지토리 안에 있습니다.

심화 — 컴포넌트 레벨 상세 구조

위 흐름도를 실제 애플리케이션에 얹으면 아래 모양이 됩니다. 핵심은 세 개의 사이클(대기·입장·주문)이 서로를 직접 호출하지 않고, Redis 키 두 개로만 만난다는 것입니다.

사이클주도자흐름특징

명령·시간 복잡도 — 최악의 단일 명령이 유계인가

Redis는 싱글 스레드라 명령 하나가 도는 동안 다른 모든 클라이언트가 기다립니다. 그래서 점검 기준은 평균 속도가 아니라 "가장 느린 단일 명령이 유계(bounded)인가"입니다. Sorted Set은 내부적으로 해시 테이블(member→score, O(1))과 스킵 리스트(score 정렬 + span으로 순위 계산, O(log N)) 두 구조를 동시에 유지하며, 아래 복잡도는 전부 여기서 나옵니다.

유저가 유발하는 모든 명령이 O(log N) 이하이고, 유일하게 자라는 스케줄러의 M은 프로퍼티로 쥔 상수입니다. 대기 인원이 얼마가 되든 개별 명령 비용은 사실상 상수 — "대기열 경로는 Redis-only 초경량"이라는 주장의 수치적 근거입니다. 토큰 TTL 만료도 접근 시 lazy 확인(O(1)) + 백그라운드 샘플링이라 우리 코드 비용은 0입니다.

금지 명령 목록 — 위험은 코드가 아니라 운영 습관에서 들어온다 설계에는 O(N) 명령이 없지만, 운영 중 손버릇이 사고를 냅니다. ① KEYS entry-token:* 절대 금지(전 키스페이스 동기 스캔 — 유효 토큰 수 세고 싶으면 SCAN 또는 발급−소모 카운터), ② ZRANGE queue:orders 0 -1 금지(대기열 전체 나열 O(N) — 인원수는 ZCARD, 구경은 LIMIT 걸린 ZRANGE 상위 일부만), ③ 거대 ZSET에 DEL 금지(동기 메모리 해제 O(N) — 초기화는 비동기 UNLINK로).

OPTION 2 · COUNTER — 진짜 경쟁자

② Serving Counter — 번호표와 전광판

은행 창구 모델입니다. 줄이라는 자료구조가 없습니다 — 유저는 불변 번호표를 받고(INCR), 입장은 유저를 꺼내는 게 아니라 "몇 번까지 입장"이라는 전광판 숫자를 올리는 것입니다. AWS Virtual Waiting Room의 공식 아키텍처입니다.[3]

강점 원자성 문제가 아예 없음

모든 연산이 O(1) 원자 명령(INCR, GET)입니다. 유저를 꺼내지 않으니 ①의 증발 문제가 구조적으로 존재하지 않고, 메모리도 카운터 2개면 끝. 폴링 부하에도 가장 강합니다.

약점 내장 기능이 없어 다 만들어야 함

중복 진입 방지(userId→번호 매핑), 이탈자 보정(번호표 받고 사라진 유저만큼 serving 추가 증가 — AWS queue_pos_expiry[4]), 전체 대기 인원 계산을 전부 별도로 구현해야 합니다.

채택 사례 AWS Virtual Waiting Room 솔루션의 공식 아키텍처입니다 — 클라이언트는 자기 번호와 serving_num을 비교하며 폴링하고, inlet 로직이 counter를 올립니다.[3] 하류 사용률 알람이 정상일 때만 counter를 올리는 자동 게이트까지 붙습니다.
3

OPTION 3 · LOG — 탈락안

③ 메시지 큐(Kafka) — 로그에 맡긴다

대기열을 브로커의 append-only 로그로 보는 관점입니다. 진입 요청을 토픽에 쌓고, 컨슈머가 하류가 감당하는 속도만큼만 소비하면서 토큰을 발급합니다. Back-pressure 관점만 보면 가장 자연스러운 모델입니다.

강점 내구성과 유량 제어

디스크 영속이라 브로커가 재시작해도 줄이 안 사라집니다(Redis 휘발성과 대비[6]). 소비 속도 = 입장 속도라 back-pressure가 별도 스케줄러 없이 구조로 구현되고, R7 Kafka 인프라를 재사용할 수 있습니다.

약점 순번 조회가 안 됨 — 탈락 사유

로그 중간을 들여다볼 수 없어 "내 앞에 몇 명?"에 답하려면 결국 Redis 같은 상태 저장소를 옆에 둬야 합니다. 그 순간 ①/②에 Kafka를 얹은 복잡도가 되고, 순번 조회 Must와 정면 상충합니다.

탈락 판정 실시간 순번 조회(Step 3 Must)가 탈락 사유의 전부이자 충분조건입니다. "대기 결과를 나중에 알려줘도 되는" 워크로드(R7 쿠폰 발급이 정확히 이것)라면 최선이지만, "지금 내 앞에 몇 명인지"를 계속 보여줘야 하는 대기열에는 자료구조가 맞지 않습니다. 같은 Redis+Kafka 조합이라도 여기어때 쿠폰 시스템처럼 Redis가 게이트, Kafka는 후처리로 역할을 나누는 게 정석입니다.[7]

DECISION

판단 — 무엇을 만들고, 무엇을 이식하나

구현은 ①로 확정(과제 명시 + Must 내장 + 사내 선례). 하지만 ②를 이해한 채로 ①을 만드는 것과 모르고 만드는 것은 결과물이 다릅니다 — ①의 모든 약점에는 ②에서 가져올 처방이 있습니다.

①의 약점②의 처방우리 구현에 이식
꺼냄→발급 원자성 구멍꺼냄 자체가 없음ZPOPMIN + SET을 Lua로 원자화 (결정 ⑩)
토큰 재요청 어뷰징generate_token 멱등[3]SET NX — 재요청 시 기존 토큰 반환
만료 유저만큼 유량 손실queue_pos_expiry 자동 보정[4]만료분만큼 다음 배치 추가 발급
폴링 스파이크counter 읽기 O(1)로 버팀서버 지정 폴링 주기(nextPollSeconds) + jitter
블로그의 척추 글의 구조가 이 문서 그대로입니다 — "Sorted Set으로 만들었다"가 아니라 "Serving Counter와 견줘보니 이 구멍이 보였고, 그래서 이렇게 막았다". ③의 탈락 사유(순번 조회 불가)는 한 단락, ②와의 대비는 본문 전체를 끌고 갑니다.
→ 실행으로구현 체크리스트 — Step 1·2·3 + 결정 현황이 문서의 판단이 체크리스트 확정/열린 결정에 매핑되어 있습니다.
